# mining-proxy

Прозрачный Stratum-прокси со статистикой шар: перехватывает TCP майнеров
через iptables DNAT, проксирует в реальный пул и
считает принятые/отклонённые/потерянные шары, отдавая их в JSON `/status`.

Без комиссии сообщения Stratum передаются без изменений. При включённой
комиссии прокси управляет авторизацией и заданиями, как описано ниже.
TLS майнера проходит байтовой трубой. Мониторинг работает на уровне
открытых Stratum V1 JSON-строк: `mining.submit` ↔ ответ пула.

## Возможности

- прозрачный перехват (`iptables DNAT` + `SO_ORIGINAL_DST`), майнеры
  не настраиваются вообще;
- счёт шар на воркерах: `submits / accepted / rejected / lost / staled`,
  процент принятия, сложность из `mining.set_difficulty`, хешрейт;
- `lost` — шары, на которые пул не ответил (обрыв/молчание);
- HTTP-мониторинг: `GET /status` (JSON) и `GET /health`;
- fail-open: при остановке правила DNAT снимаются, майнеры уходят
  в пул напрямую, майнинг не прерывается.

## Сборка и запуск

```sh
go build -o mining-proxy .
./mining-proxy --config config.local.yaml
```

Конфиг: см. [`config.example.yaml`](config.example.yaml). Обязательные
поля при `setup_iptables: true` — `allowed_subnets`; `upstream_pool`
нужен как fallback и для DNAT-фильтра по порту.

Порядок старта: конфиг → listener (порт занимается до DNAT, чтобы
майнер не получил RST в промежутке) → iptables → приём соединений →
мониторинг. При SIGINT/SIGTERM соединения дожидаются, правила снимаются.

## Мониторинг

```sh
curl -s http://127.0.0.1:9090/status | jq
curl -s http://127.0.0.1:9090/health
```

Пример `/status`:

```json
{
  "status": "ok",
  "listen_addr": "0.0.0.0:8443",
  "totals": {
    "connections_active": 12,
    "connections_total": 340,
    "submits": 1200, "accepted": 1198, "rejected": 2,
    "lost": 0, "staled": 0,
    "accepted_percent": 99.83,
    "difficulty": 16,
    "hashrate": 1374389534720
  },
  "pools": [ ... ],
  "workers": [ ... ],
  "nat": { ... }
}
```

`monitor_addr` по умолчанию слушает только `127.0.0.1` — наружу не
выставляйте без firewall.

## systemd

```sh
sudo cp mining-proxy /usr/local/bin/
sudo cp config.example.yaml /etc/mining-proxy/config.yaml   # и поправить
sudo cp mining-proxy.service /etc/systemd/system/
sudo systemctl daemon-reload
sudo systemctl enable --now mining-proxy
journalctl -u mining-proxy -f
```

## Тестовый стенд

Мок-пул и эмулятор майнера:

```sh
go run ./testrig/mockpool -listen 127.0.0.1:3333 -difficulty 16
# -reject — отклонять все шары; -silent — не отвечать (тест lost)

go run ./testrig/miner -proxy 127.0.0.1:8443 -worker test.worker \
  -sps 5 -shares 100
```

Проверка полного цикла комиссии на 1/10/50/100 модельных ASIC:

```sh
go test ./proxy -run TestCommissionReauthorizationLoadModel -count=1 -v
```

Для 1000 и 10 000 одновременных соединений:

```sh
MINING_PROXY_LARGE_LOAD=1 go test ./proxy -run TestCommissionReauthorizationLoadModel -count=1 -v -timeout 5m
```

Нагрузочный тест отключает ограничитель частоты входа в комиссию, чтобы все
соединения одновременно прошли переходы. В рабочем режиме допуск ограничен,
но ожидание очереди не задерживает шары; возврат авторизации не ограничивается.

Тест сравнивает комиссию включённую и выключенную. Его mock-пул выдаёт job
на каждое соединение и инвалидирует прежний job при `mining.authorize`;
результаты отражают именно этот сценарий, а не точную политику конкретного
производственного пула.

При включённой комиссии прокси выдаёт ASIC свои идентификаторы заданий и
восстанавливает исходные ID при отправке в пул. Это отделяет задания разных
авторизаций, даже если пул повторно использует ID. Комиссия начинается после
ответов на обычные шары, подтверждения авторизации и нового задания; первый
notify после перехода всегда получает `clean_jobs=true`. Фактическая сложность
передаётся перед соответствующим заданием. Ожидания `suggest_difficulty` нет.

После последней отправленной комиссионной шары прокси дожидается ответов
на все комиссионные submit и закрывает соединение (`batch_complete` в логе).
ASIC переподключается под своим воркером и заново получает subscribe,
extranonce и задание. Успешное завершение порции не включает предохранитель:
следующие интервалы продолжают собирать комиссию. Это предполагает паузу
переподключения; её длительность зависит от прошивки ASIC.

Шары основного воркера, оставшиеся в очереди ASIC при входе в комиссию,
получают явный stale-ответ и учитываются в rejected. Такой переходный stale
не отключает комиссию и не засчитывается фиктивно принятым. Вход по-прежнему
требует подтверждения authorize и нового задания. Notify, пришедший до
подтверждения, сохраняется вместе со своей сложностью и активируется после
подтверждения; уже известное задание предыдущей авторизации так не переносится.

Настоящий отказ авторизации, таймаут подготовки или неожиданный обрыв во время
комиссии блокирует повторные попытки до перезапуска для пула и исходного IP
ASIC. Это предотвращает цикл переподключений при смене адресов неподдерживаемого
пула. Обычный EOF вне комиссии и запланированное завершение порции не блокируют
сбор. Состояние видно в `commission.disabled_sources` и
`commission.pools[].disabled_reason`. `commission.enabled` означает включение
в конфигурации, а не наличие фактического изъятия на каждом пуле.

Процент комиссии по-прежнему относится к числу шар: при разных сложностях
основного и комиссионного воркера доля work может отличаться.

Диагностические `[DIAG]` записи агрегируют отказы шар по пулу, категории и
режиму авторизации, а также `mining.notify` и ответы `subscribe`/`authorize`.
Они ограничены по частоте и не пишут отдельную строку на каждую шару или job,
чтобы сбор логов оставался пригодным для тысяч соединений.

Для диагностики переключений дополнительно записываются:

- `connection_end`: этап, первый наблюдавшийся источник завершения
  (`observed_side`), причина, подтверждение авторизации и факт notify до ответа;
- `commission_authorize` и `commission_notify`: порядок ответа авторизации
  и нового задания; новое notify до подтверждения сохраняется до ответа;
- `miner_handshake`: название клиента из subscribe, имена запрошенных configure
  extensions и запрос `mining.extranonce.subscribe`;
- `pool_extranonce`: размеры extranonce из subscribe и первого set_extranonce.

Пароли, значения configure и содержимое extranonce не записываются.
Отсутствие запроса `mining.extranonce.subscribe` не доказывает отсутствие
поддержки смены extranonce прошивкой. Этот диагностический режим ещё не
реализует переключение на отдельное комиссионное соединение.

## Тесты

```sh
go test ./...        # unit + e2e (mock-пул → прокси → клиент)
go test -race ./...
```

Структура:

- `config/` — YAML-конфиг и валидация;
- `proxy/` — слушатель, сессии, парсер Stratum V1, реестр статистики;
- `iptables/` — настройка/снятие DNAT, статус перехвата;
- `monitor/` — HTTP `/status`, `/health`;
- `tests/` — интеграционные сценарии (accept/reject/lost, raw-passthrough);
- `testrig/` — мок-пул и эмулятор майнера.
